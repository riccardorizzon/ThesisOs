# ADR-0012: External Infrastructure Schemas

- Status: Accepted (frozen 2026-06-24)
- Context: M1 wires LangGraph with a `PostgresSaver` checkpointer for conversation state persistence and restart recovery. `PostgresSaver.setup()` creates and migrates its own tables (`checkpoints`, `checkpoint_writes`, `checkpoint_blobs`) whose structure is owned by the `langgraph-checkpoint-postgres` library and can change between versions. ThesisOS governs its **domain** schema through `contracts/db/schema.sql`, Alembic migrations, and a drift test that asserts the SQLAlchemy models match the canonical schema. Pulling library-owned tables into Alembic/`schema.sql` would couple our domain contract to LangGraph's internal schema and would make the M0 `contracts: unchanged` gate fail for a non-domain reason.
- Decision: Distinguish **domain schema** (owned by ThesisOS) from **infrastructure schema** (owned by external tools). The LangGraph checkpoint tables are infrastructure: they live in a dedicated `langgraph` Postgres schema (falling back to documented `public` tables only if the installed checkpointer version does not support a custom schema), are created/migrated exclusively by `PostgresSaver.setup()` at application startup, and are **excluded** from Alembic and from the schema drift test. The domain stays in `public` exactly as frozen in M0 — no new `users` table, no schema rename. `contracts/db/` gains a `langgraph-owned.md` note documenting ownership, creation mechanism, and the excluded table list. The promotion gate phrase `contracts: unchanged` is read as `domain_contracts: unchanged`, not `all_database_objects: unchanged`.
- Consequences: PostgresSaver can be introduced immediately in M1 with durable checkpoints and restart recovery, without polluting the domain model or breaking the drift test (which scans only ThesisOS-owned tables). Ownership is unambiguous: ThesisOS owns models/migrations/contracts; LangGraph owns its checkpoint persistence; there is no overlap. The trade-off is that two systems write to one database, mitigated by schema-level namespacing and the explicit ownership note. If a future tool needs its own tables, it follows the same pattern.
- Alternatives considered: (a) Manage the checkpoint tables in an Alembic migration — rejected because it couples our domain schema to LangGraph's internal, version-dependent table layout and invites breakage on upgrade. (b) Implement a custom checkpointer over a ThesisOS-owned table — rejected as avoidable work that reimplements a maintained library for no M1 benefit. (c) Let the tables land unmanaged in `public` with no documentation — rejected because undocumented foreign tables erode the meaning of the domain contract and the drift gate.
