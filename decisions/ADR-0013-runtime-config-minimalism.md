# ADR-0013: Runtime Configuration Minimalism

- Status: Accepted (frozen 2026-06-24)
- Context: M0 provisioned an (empty) `vertex-config` Secret Manager secret in anticipation of runtime LLM configuration. In M1 the only runtime LLM need is to call Gemini on Vertex AI through LiteLLM. LiteLLM reaches Vertex using Application Default Credentials (already present locally and via the Cloud Run service account) plus `GOOGLE_CLOUD_PROJECT` and `VERTEX_LOCATION` (already wired as Cloud Run env) and `gemini_model` (already a default in `app/core/config.py`). Populating `vertex-config` now would duplicate `config.py`, add a second source of truth, increase drift risk, and add an operational component that delivers no M1 value.
- Decision: M1 authenticates to Vertex with ADC only and reads model/project/location from environment + `config.py`. The `vertex-config` secret is **not** populated or read in M1. `config.py` is the single source of truth for runtime LLM configuration. Secret Manager is avoided for LLM config until a concrete need appears (multi-provider fallback, dynamic routing, per-environment temperature/token limits, per-agent models, A/B testing) — at which point `vertex-config` can be introduced without breaking anything, since callers already go through the LiteLLM seam.
- Consequences: The M1 path is `Cloud Run → service account → ADC → LiteLLM → Vertex`: one credential, no API keys, no JSON secret, no duplicated config. The M1 gate requires `adc: working`, `google_cloud_project: set`, `vertex_location: set`, `litellm: working`, `streaming: working` — and explicitly does **not** require a populated `vertex-config`. The trade-off is that richer runtime configuration is deferred, accepted under YAGNI because the LiteLLM seam keeps that door open.
- Alternatives considered: Populating `vertex-config` now with `{project, location, model}` JSON and reading from it — rejected because it duplicates `config.py`, creates a second source of truth and drift risk, and adds complexity with no value at M1.
