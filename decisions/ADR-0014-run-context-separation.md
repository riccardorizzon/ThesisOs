# ADR-0014: RunContext Separation

- Status: Accepted (frozen 2026-06-24)
- Context: The frozen `GraphState` (ADR-0007) is the domain state threaded through the graph: `messages`, `plan`, `route`, `retrieved_context`, `draft`, `citations`, `memory_ops`, `critique`, `task`, `errors`. Execution-time concerns — which conversation/run this is, the trace id, the request id — are a different category of data. If execution identifiers are pushed into `GraphState`, the domain contract bloats with non-domain fields, every checkpoint serializes transport metadata, and later milestones (M12 multi-agent) would mutate the frozen state shape to carry orchestration plumbing.
- Decision: Introduce a `RunContext` value object, kept strictly separate from `GraphState`. `GraphState` carries domain reasoning state only (unchanged from M0). `RunContext` carries execution metadata: `conversation_id`, `agent_run_id`, `trace_id`, `request_id`, `user_id: str | None = None` (always `None` while single-user per ADR-0001), and `metadata: dict`. `RunContext` is passed alongside the graph invocation (e.g. as LangGraph config/`configurable`), not embedded in `GraphState`. It is **runtime-only**: it MUST NOT be persisted into the LangGraph checkpoint — checkpoints carry domain working state, while execution metadata lives only for the duration of the run. Mixing the two is forbidden: domain fields never go into `RunContext`, execution fields never go into `GraphState`.
- Consequences: `GraphState` stays frozen and serializes cleanly into checkpoints without transport noise; execution metadata (tracing, correlation, future per-run accounting) has a stable home that can grow independently. Token accounting and run-level bookkeeping attach to `agent_runs`/`RunContext`, not to `messages`, so future per-agent token consumption (planner, retriever, critic) records naturally without touching domain rows. The cost is one extra object to thread through the call path, accepted as the clean execution/domain boundary that M12 will rely on.
- Alternatives considered: (a) Put execution ids directly on `GraphState` — rejected because it changes the frozen domain contract and pollutes every checkpoint with transport data. (b) Pass loose keyword arguments (conversation_id, trace_id, …) through every layer — rejected because an unstructured, ever-growing argument list is error-prone and has no single contract. (c) Defer `RunContext` until M12 — rejected because retrofitting an execution-context boundary after services and the graph are built is exactly the rewrite the seam-first strategy avoids.
